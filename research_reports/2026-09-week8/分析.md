### 2.2 结果：τ 存在明确最优区间

| τ/T_burst | ρ≈0.40 丢包 | FDL 使用率 | ρ≈0.59 丢包 | FDL 使用率 |
|---|---|---|---|---|
| 0.25 | 10.79% | 3.3% | 16.32% | 4.8% |
| 0.50 | 9.09% | 6.4% | 14.76% | 9.0% |
| **1.00** | **6.78%** | 12.0% | **13.51%** | 15.3% |
| 2.00 | 8.35% | 15.4% | 16.38% | 19.4% |
| 3.99 | 11.74% | 20.9% | 19.61% | 24.2% |
| **No-FDL** | **12.88%** | — | **18.71%** | — |

三条可直接写进 5.1 的结论：

1. **最优在 τ/T_burst ≈ 1**，两档负载一致（ρ=0.40 时 −6.10 pp，ρ=0.59 时 −5.20 pp）。
2. **延迟线太长不但无益，还可能有害**：ρ=0.59、τ/T=4 时丢包 19.61% **高于**不加 FDL 的 18.71%。
3. **FDL 使用率随 τ 单调上升**（3.3% → 24.2%），但丢包先降后升 —— 也就是"用得更多 ≠ 效果更好"。
   这是 5.1 最有说服力的一张图：它把"收益边界"从直觉变成了数据。

## 三、途中查出的红线缺陷：`maxFdlLoopsPerBurst` 设成了无限制

### 3.1 现象

第一遍跑完，分析脚本的健全性检查报警：

```
total burstsLoopedMultiple across all runs = 147935 (must be 0)
```

`AGENTS.md` 红线写明"**单次回环**：FDL 最大回环次数为 1，不实现多次回环"，
但 `fdl_params.ini` 里是：

```ini
**.sat*.coreSwitch.maxFdlLoopsPerBurst = -1     # -1 = 无限制
```

代码逻辑是 `if (maxFdlLoopsPerBurst >= 0 && bcp->getFdlLoopCount() >= maxFdlLoopsPerBurst) fdlAllowed = false;`
—— 取 -1 时这个判断永不成立。而 **BCP 携带 `fdlLoopCount` 跨节点传递**，
所以一个突发可以在**沿途每个节点各回环一次**（最长 5 跳就是 5 次）。

### 3.2 配对探针量化

同种子、同单元，只改这个参数（ρ≈0.59）：

| τ | `loops=-1` | `loops=1` | 差 |
|---|---|---|---|
| 34.4 µs（τ/T=1） | 12.64% | **13.48%** | +0.84 pp |
| 137.4 µs（τ/T=4） | 23.30% | **19.61%** | **−3.69 pp** |
| 多次回环次数 | 21,818 / 41,997 | **0** | — |

结论：**这不是表面问题，最大改变 3.7 个百分点**；但定性结论活了下来
（τ/T=4 仍然差于 No-FDL 的 18.71%，只是差距从 4.6 pp 缩到 0.9 pp）。

### 3.3 处置

1. `fdl_params.ini` 改为 `**.sat*.coreSwitch.maxFdlLoopsPerBurst = 1`，并把探针数据写进注释。
2. **重跑整个 ExpA 批量**（50 run，1366 s）→ 第二节的表格即修正后结果，`burstsLoopedMultiple = 0` ✓
3. 第一遍（多回环版）数据保留在 `results/ExpA-TauSweep-multiloop-2026-09-18/` 作为对照证据。
4. 折进 `fdl_tests.ini` 两个常驻诊断配置：
   - `Test-FDL-Diag-LoopStrict` → `burstsLoopedMultiple` **必须 0**（实测 0 ✓）
   - `Test-FDL-Diag-LoopLoose` → **预期 >0**（实测 41,997 ✓，与探针一致）

## 四、热点流量标定：ρ≥0.8 达成

### 4.1 先搞清拓扑与瓶颈

去 sat2 的流量分三路（据各核心路由表）：

| 到 sat2 的入口 | 源 |
|---|---|
| 经 **sat3** | sat3, sat6, sat7, sat9, sat10（**5 个**） |
| 经 sat1 | sat1, sat4 |
| 经 sat5 | sat5, sat8 |

热点矩阵（9 源全发 sat2）本来就把 5 个源压在同一条链路上，所以 **瓶颈恒为 sat3 port1（sat3→sat2）**。

### 4.2 粗扫（40 run）+ 细扫（16 run）

| 发送间隔 | 瓶颈 ρ | 种子有差异 |
|---|---|---|
| 35.6 µs | 0.6245 | ✓ |
| 25 µs | 0.7253 | ✓ |
| 21.3 µs | 0.7764 | ✓ |
| 20.5 µs | 0.7888 | ✓ |
| 20 µs | 0.7967 | ✓ |
| **19.5 µs** | **0.8074** | ✓ |
| 19 µs | 0.8146 | ✓ |
| 18 µs | 0.8327 | ✓ |
| 15 µs | 0.8936 | ✓ |
| 12 µs | 0.9455 | ✗ **完全相同** |

**第三档负载点定为 19.5 µs → ρ ≈ 0.807**，已回写 `FDL-Hotspot` 的 `meanInterval` 扫描。

### 4.3 两个值得记的观察

1. **中途我一度以为 ρ 封顶在 0.78**：只扫到 21.3 µs 时看起来饱和了（丢包已 34.65%）。
   继续缩短间隔证明是误判 —— 18 µs 就上到 0.83，15 µs 到 0.89。
   教训：**"看起来饱和"要扫穿才敢下结论。**
2. **12 µs 时 4 个种子的 ρ 完全相同**（0.9455）且最忙节点在 sat1/sat4 之间跳变 ——
   链路被完全占满，ρ 钉在天花板上，与种子无关。这说明 12 µs 已超出可用工作区，
   不适合作为负载工作点。

## 五、D1 的处置：**改为公开文献建表，已闭合**（2026-09-20）

用户决定**不向他人询问**（"问的人不一定准确"），改为从公开文献与厂商资料建器件参数表。
详细交付见 [`器件参数与三条不等式.md`](器件参数与三条不等式.md)。

### 为什么这个方向更好

盘查后发现：原 D1 询问稿问的 7 个参数里，**只有"质量/体积/功耗预算"一个真正在别人手上** ——
其余分别来自设计选择（τ_max = 级数 × 步进）、标准光纤参数（0.2 dB/km）或**厂商资料**。

器件参数取自 **Mouammar 2026 TABLE II 及其原始出处**（已登记 `refs.bib`）：

| 参数 | 光束转向 | MEMS | 电光 | InP SOA |
|---|---|---|---|---|
| 出处 | HUBER+SUHNER Polatis 6000s | 桂林 GLsun 4×4 级联 | Agiltron 4×4 高速 | Feyisa 等, *JLT* 40(19) 2022 |
| 切换时间 | 25 ms | 8 ms | **0.1 µs** | **5.2 ns** |
| 功耗 | 5 W | 1.25 W | 10 W | **0.58 W** |
| 每级插损 | 1 dB | 2.6 dB | **3.5 dB** | **0 dB** |
| 成熟度 | 商用 | 商用 | 商用 | 实验阶段 |

### 三条不等式（用 `fdl_design.py` 器件模式算）

1. **τ ≥ 切换时间**：扫描区间最小点 0.859 µs（10 Gbps 设计点）是电光切换时间的 8.6 倍、SOA 的 165 倍。
   **MEMS 被定量排除** —— τ ≥ 8 ms 等价于 τ/T_burst ≈ 2.3×10³，而实测最优在 1，差 3 个数量级。
2. **累计插损 ≤ 链路预算余量**：τ/T_burst=1 需 3 级（步进 0.5 µs）。电光 → **10.64 dB**；InP SOA → **0.14 dB**。
   这是"成熟度 vs 链路预算"的取舍。
3. **级数 ≤ 质量/体积上限**：**唯一仍开放** —— 厂商表无质量体积数据，改为显式假设 + 敏感性。

### 两处必须更正的旧假设

| 项 | 旧 | 新（有出处） |
|---|---|---|
| 每级插损 | 0.5 dB | **3.5 dB/级**（电光）—— 旧值**乐观 7 倍**；`fdl_design.py` 默认值同样过乐观 |
| 开关候选 | 默认电光 | 电光 ✅ / InP SOA ✅（插损极低但实验阶段）/ MEMS 与光束转向 ✗ |

### 附带收获（对新颖性）

Mouammar 原文第 138–145 行明确写道：**OPS/OBS "not technologically mature due to the need for optical buffering"**，
故其采用 "OBS with path reservation (no contention resolution at nodes)"。全文检索确认该文**未出现 FDL / 光纤延迟线**。

这为论文 2.2 节"卫星 OBS 文献回避星上缓存，依据是工程直觉而不是量化对照"提供了**可直接引用的原文**。

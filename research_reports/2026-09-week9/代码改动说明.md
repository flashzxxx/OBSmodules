## 一、对照维度 1：VF 调度器选项（Horizon + void filling）

### 1.1 `src/CoreNode/OBS_ChannelCalendar.h`（新增，83 行）

存"信道还空不空"的数据结构，只替换了"用什么存"，没有改调度规则。

- **`struct OBS_ChannelReservation`**：一个信道上的**一条预约**，即一个 burst 在 OXC 上占用的窗口 `[start, end]`。窗口就是 `OBS_CoreControlLogic` 写给 OXC 的预约区间 `[burstArrival − guardTime/2, burstArrival + burstDuration + guardTime/4]`，因此任意两条预约**可以相切、不可重叠**——这个不变量与标量 horizon 维持的是同一个，是本选项能成为"Horizon 的严格推广"而不是第二个调度器的根源。
- **`class OBS_ChannelCalendar`**：
  - `calendars[port][lambda]`：三层 vector，每个信道一份按 start 排序、互不相交的预约列表。第 `numPorts` 号 port 是 **FDL 回环的伪信道**（与 `OBS_CoreOutputHorizon` 对 FDL 的记法一致），使 FDL 本身也能被补空。
  - `setChannelCounts(numPorts, lambdasPerPort)`：按各输出端口的波长数分配日历；任一端口的信道数为 0 会**响亮报错**（见 1.5 的缺陷修复，0 信道会让所有查询越界读并静默拒绝每个 burst）。
  - `setPruneMargin(margin)`：设置头部清理（front pruning）的保守裕量，`fits()` 查询窗口最多只会回看到 `burstArrival − guardTime/2`，裕量取 `guardTime` 足够安全。
  - `fits(port, lambda, start, end)`：判 `[start, end)` 是否与该信道现有预约**全都不重叠**。
  - `findFittingLambda(port, start, end)`：返回该端口第一个能装下窗口的 lambda，找不到返回 -1（对应 `*` 路由选色）。
  - `reserve(port, lambda, start, end)`：登记一条预约。
  - `getScanCount()` / `getMaxReservationCount()`：两个**复杂度证据**标量——`scanCount` 是区间比较总次数（LAUC-VF 的成本代理），`maxReservations` 是任一信道上同时存在的最大预约数（即 W=1 下实际要"看的空隙数"）。两者都用于回答算力红线的"星上算得起吗"。
  - `isEnabled()`：日历是否已建立。

### 1.2 `src/CoreNode/OBS_ChannelCalendar.cc`（新增，149 行）

文件头注释（第 21–47 行）是本周关键推导的源码化存档：

- 标量 horizon 的接纳判据 (H)：`horizon ≤ burstArrival`，是**只追加**规则。
- 日历的接纳判据 (V)：新窗口与每条已有预约都不重叠。
- 若最后一条预约是 `[A0−g/2, A0+D0+g/4]`，则标量模型记下的 `horizon = A0+D0+3g/4 = (A0+D0+g/4) + g/2 = r.end + g/2`，于是 (H) 展开为 `A − g/2 ≥ r.end`——正是 (V) 的第一支。
- **结论：信道无空隙时两规则判定完全相同；VF 只能多接纳（补进空隙的），不可能少接纳。** 没有空隙可补的运行（同步偏移场景）两个调度器逐标量一致。

方法实现要点：

- `setChannelCounts()`：端口 0..numPorts 全部建表，数据端口的波长数取自传入参数，FDL 伪端口固定 1 信道；`lambdas < 1` 直接 `opp_error`。
- `checkChannel()`：所有入口共用的越界检查，越界 `opp_error` 而非静默继续——本类一旦尺寸错了，错的不是"少数 burst"而是"全部 burst"。
- `pruneChannel()`：头部清理。仅当信道预约数 ≥ `OBS_CALENDAR_PRUNE_THRESHOLD`（64）才做 `erase`（O(n) 的 memmove 只有值得时才做），删掉 `end < simTime() − pruneMargin` 的过期预约；已过期预约不可能再与任何未来查询窗口重叠，删除安全。
- `fits()`：从前往后扫描；列表按 start 排序，所以**一旦某条预约的 start ≥ 查询窗口 end，后面不可能再有重叠，直接返回 true**（提前退出）。这个提前退出使成本正比于"到达时刻之前的空隙数"，即 LAUC-VF 的性质，也是星上算力预算要对照的复杂度声明。每次比较计一次 `scanCount`。
- `findFittingLambda()`：按 lambda 序号逐个问 `fits()`，返回第一个能用的。W=1 下每端口只有一个数据信道，多信道排序不属于任何实验结果。
- `reserve()`：从头部线性找插入点（预约几乎总是追加，常见情况 O(1)；补空隙时才真正走表），插入后做 `pruneChannel()`，再刷新 `maxReservations`（测的是**活集**大小而非清理前峰值，这才是"要看的空隙数"的正确口径）。

### 1.5 `src/CoreNode/OBS_CoreControlLogic.cc`（+91 行，−12 行）

**`initialize()`**：

- 从 CoreNode 读 `enableVoidFilling`（ini 写法 `**.sat*.coreSwitch.enableVoidFilling`，与 `useFDL` 同层），`WATCH` 之。
- `voidFilledBursts = 0` 初始化。
- **日历只在选项打开时建立**，且信道数从 `coreOutput->par("lambdasPerPort")` 的字符串解析（代码注释与报错文案称 `lambdasPerOutPort`）。**为什么不能从 `gatesHorizon->getPortLambdas()` 取**：`GatesHorizon` 在 `OBS_CoreControlUnit.ned` 里声明在 `ControlLogic` 之后，`initialize()` 尚未执行、数组还是空的——首版就是这么写的，日历建成 0 信道，所有接纳查询越界读、每个 burst 都被静默拒绝（`Test-VF-On` 上发现，2026-09-20 修复）。现在 token 数与端口数不符也 `opp_error`。
- `setPruneMargin(guardTime)`。

**三个谓词方法**：

- `channelAccepts()`：选项开 → `calendar.fits(port, lambda, windowStart, windowEnd)`；选项关 → 原样的 `gatesHorizon->getHorizon(port, lambda) <= burstArrival`。
- `selectLambda()`：选项开 → `calendar.findFittingLambda(...)`；选项关 → 原样的 `findNearestLambda(port, burstArrival)`。
- `reserveChannel()`：**horizon 永远更新**（这是基线行为，两个对照维度都如此）；选项开时**另外**把窗口记进日历。回环的两段预约（输入门→FDL、FDL→目标门）都从这里走，所以 FDL 伪信道也被日历管理。

**`handleMessage()` 的四条决策路径改走谓词**（原来直接摸 `gatesHorizon` 的四处）：

| 路径 | 原来 | 现在 |
|---|---|---|
| `*` 路由选色 | `findNearestLambda(outPort, burstArrival)` | `selectLambda(...)` |
| `*` 路由 + 场景 B（FDL 回环） | `fdlHorizon <= burstArrival` 且 `findNearestLambda(outPort, burstArrival+tau)` | `channelAccepts(numPorts, 0, ...)` 且 `selectLambda(outPort, burstArrival+tau, ...)` |
| 固定颜色直通 | `getHorizon(outPort, lambda) <= burstArrival` | `channelAccepts(outPort, lambda, ...)` |
| 固定颜色 + 场景 B | `waitTime <= tau && fdlHorizon <= burstArrival` | `channelAccepts(numPorts, 0, ...) && channelAccepts(outPort, lambda, burstArrival + tau, ...)` |

固定颜色场景 B 的改法值得注意：无空隙时 "信道在 `burstArrival+tau` 时空" 与 "等待时间 ≤ τ" 等价，所以选项关时行为不变；选项开时它允许"τ 之后有空隙即可入环"。

**预约落账的三处**（原 `updateHorizon` 三处）全部换成 `reserveChannel(...)`：主预约、FDL 伪信道预约（`newFDLHorizon`）、延迟后的目标门预约（`delayedArrival`）。

**计数**：`countStats` 块里，选项开且 `burstArrival < gatesHorizon->getHorizon(outPort, lambda)` 时 `voidFilledBursts++`——即"信道此时尚未空闲、只追加规则必然拒绝"，这个数才是 VF 真正补了多少。

**`finish()`**：VF 专属标量**只在选项打开时记录**：

```
voidFilledBursts / calendarScanCount / calendarMaxReservations
```

这是"默认运行 `.sca` 与改动前逐标量全同"能成立（而不是"容差内"）的原因之一——关掉时连标量都不新增。

### 1.6 默认路径为什么保证未变

选项关时：`channelAccepts` 即原判据、`selectLambda` 即原函数、`reserveChannel` 即原 `updateHorizon`、日历不分配不访问、VF 标量不记录。回归（debug，改动前后同模式对照）：Basic/TooShort/Off/SO 各 **1701/1701** 标量相同、Compatibility **1697/1697** 相同，差异 0、新增标量 0。注意 `.sca` 不能跨构建模式比较（release 重跑会出现 79–84 条末位浮点差异，与代码无关，见 `分析.md`）。

## 二、对照维度 2：host 侧无缓存重传基线（实验 R，论文 5.2 节）

设计动机：对照 No-FDL 时，"核心节点冲突即丢、从不重试"的 No-FDL 是个稻草人——文献里"不加光缓存"的工程路线（Zhao 2022 等）是**让源端在时间域恢复**。这个对照维度把恢复从光域（交换机里的 FDL）搬到时间域（源端 ARQ），代价是每请求多一个要穿过同一套拥塞星座的确认包。

### 2.1 `src/Retransmit/OBS_RetransmitPacket.msg`（新增，34 行）

```
packet OBS_RetransmitPacket {
    int seq = -1; //Request sequence number. The acknowledgement echoes the number it answers.
}
```

- 请求与确认**共用一个包类型**，`seq` 把确认和它回答的请求配对（确认只是回显序号）。
- 做成**包字段**而不是 payload 字节，原因写在头注释：边缘 burstifier 是整包封装的，payload 字节到接收端要逐字节重解析，且确认与请求本来就不是同一个尺寸。
- `OBS_RetransmitPacket_m.cc/.h`（291/68 行）是 OMNeT++ 消息编译器从 `.msg` 生成的标准产物（`getSeq/setSeq`、marshaling），不是手写逻辑。

### 2.2 `OBS_RetransmitSource.{ned,h,cc}`（新增，68/103/251 行）

**`.ned`**：`simple OBS_RetransmitSource like IUDPApp`——继承 INET 的 UDP 应用接口（`udpIn/udpOut` 门、`IUDPApp` 全部参数：`localPort`、`destAddresses`、`destPort`、`messageLength`、`startTime`、`stopTime`、`sendInterval`），因此**配置里只换 `udpApp[i].typename` 一个词**就能把该 host 的源切到这个对照维度，场景、流量、组帧链全不动。这也保证了它不触碰受保护的 `src/EdgeNode/` 基线。两个新增参数：

| 参数 | 语义 |
|---|---|
| `retransmitTimeout` | ARQ 超时，**从最后一次发送起算**（每次重传后定时器重新调度）。必须大于最长路径 RTT，否则在途副本还没回来就先重传，测的是自己的急躁而不是网络的丢 |
| `maxRetransmissions` | 重试上限；**0 = 只发不管**，退化成"带丢失观测的 send-and-forget"，正是对照例要用的模式 |

NED 还声明了 `@signal[requestCompleted](type="double")` 与 `@statistic[completionDelay](record=mean,min,max,count)`。用四个普通 recorder 而不是 `stats`，是因为本版本 OMNeT++ 的 `stats` 记录器只写出一行无字段的 statistic 行，分析脚本读不了（注释里说明，做法与 `OBS_CoreControlLogic` 记 `burstNodeDelay` 一致）。

**`.h`**：核心是每请求的状态：

```
struct RequestState {
   int seq;             // 序号，兼作其重传定时器的 kind
   simtime_t firstSent; // 首次发送时刻，完成时延的零点
   int transmissions;   // 首发后 = 1，重传一次 = 2，…
   IPvXAddress destAddr; int destPort;
   cMessage *timer;     // 该请求的重传定时器
};
std::map<int,RequestState> outstanding; // 等待确认的请求
```

**`.cc` 的行为分三段**：

- **`sendRequest()`**（新请求流，节奏与 UDPBasicApp 相同：每 `sendInterval` 一个包、随机目的地）：分配新 `seq`，建请求包（`messageLength` 字节），入 `outstanding`，经 UDP socket 发出，同时调度 `retransmitTimeout` 后的定时器。**定时器用自消息的 `kind` 携带序号**（不自消息带 map 第二次查询，且这些消息不出模块、不与 INET 冲突）。
- **`processRetransmitTimer()`**（定时器到点）：请求仍在 `outstanding` → 重发一份同样的请求、`transmissions++`、重新调度定时器；若 `transmissions > maxRetransmissions` → 计 `requestsAbandoned`、从 map 删除（该请求判丢）。请求已被确认则定时器是残留，直接删。
- **`processAck()`**（收到确认）：按 `seq` 查 `outstanding`；查不到 → 迟到/重复确认，计 `duplicateAcks`；查到 → 计 `requestsAcked`，**发射 `requestCompleted` 信号，值为 `simTime() − firstSent`（完成时延，从首次发送算起）**，取消定时器、删状态。

`finish()` 记录的标量：`requestsSent`、`retransmissionsSent`、`transmissionsTotal`、`requestsAcked`、`requestsAbandoned`、`requestsOutstanding`、`duplicateAcks`、**`deliveryRatio = requestsAcked/requestsSent`（实验 R 的主指标）**、`goodputBps`。全部统计都按 `warmupPeriod` 窗口门控，与 `OBS_CoreControlLogic` 的利用率标量同窗口约定，两侧可直接对照；goodput 同样按"simTime() − warmup"计窗。

析构函数要取消 `sendTimer` 和**所有未决请求的定时器**——仿真结束时最后几个请求永不完成，不取消就泄漏自消息。`handleNodeStart` 里绑 socket、解析 `destAddresses`（INET `IPvXAddressResolver`，支持按名字）；`shutdown/crash` 取消发送定时器。

### 2.3 `OBS_RetransmitSink.{ned,h,cc}`（新增，43/67/95 行）

**`.ned`**：`like IUDPApp`，唯一新增参数 `ackLength`（确认包字节数，须 > 0）。

**`.cc`**：**无状态**——收到请求（`UDP_I_DATA`）后：

1. 摘掉 `UDPDataIndication` 取出**来源地址/端口**（确认必须回到那个确切 socket，源端按序号记账）；
2. 回发一个 `ackLength` 字节、**回显原 `seq`** 的确认包；
3. 计 `requestsReceived` / `acksSent`。

三个刻意的设计决定（头注释）：

- 确认**故意做得小**：它和请求走同一套已加载的星座，不能把 offered load 翻倍；但成本是真实的（每请求多一个 burst、多一个 OXC 窗口），**不藏**，直接体现在重传基线的实测信道利用率高于其新发负载上。
- **重复请求不在汇端过滤**：重传可能源于"确认本身丢了"，汇端对每个重复都重新确认；去重只能在源端做，因为 `seq` 是每源独立的，而一个汇可能服务多个源。
- 汇端因此只留两个计数标量，无其他逻辑。

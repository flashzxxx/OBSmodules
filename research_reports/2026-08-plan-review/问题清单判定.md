## 一、三个决策项：都需要做，全是文档修改

### 1. FDL 口径改为"光开关式可调延迟器"——需要做，优先级最高

这是已拍板的器件事实，而现在 `fdl_design.py` 和计划文档全按"一段固定长光纤、1 km 预算"来写。口径不改，实验 A 得出的"τ 可行上界"就建立在错误的器件模型上。

需要改的内容：

- 文档表述换成四个参数：最大延迟档、步进粒度、每级插入损耗、开关切换时间。
- `fdl_design.py` 增加多级延迟器的损耗模型：损耗 = 光纤损耗 + 级数 × 每级插损，后者通常是主导项。
- 向结构/总体专业要数值的请求确实该发，它阻塞第 9 周实验 A 可行区间上界。

### 2. BCP 1 µs 标注为假设值 + 实验 C 前敏感性扫描——需要做，成本几乎为零

判断依据与清单一致：

- 实验 A/B 里 offset 固定 500 µs，扣 1 µs 还是 5 µs 无关紧要。
- 实验 C 的结论直接是"offset 能压到多低"，`processingTime` 就是分母，必须扫。

加一个 0.5 / 1 / 5 µs 的三点扫描配置就够。可以等到实验 C 启动前（第 12 周）再写进 ini，但文档标注现在就该加：该值是假设值（assumed, to be confirmed against device datasheet）。

### 3. RateCheck 写成 go/no-go 闸门——需要做

关键理由是清单没有明说的一条：**判据必须在跑之前定**。否则跑完再看结果定判据，就有事后挑选之嫌，评审会质疑。

go/no-go（决策闸门）的含义：预设通过/不通过判据，通过才继续投入。

判据定义（吸收交叉复核修正——原判据对低丢包率不稳定，0.1% vs 0.12% 的相对偏差 20% 会触发假 no-go）：

**主判据**（稳定量，不受低丢包率放大效应影响）：

- `maxChannelUtilization` 相对偏差 < 10%；
- `fdlUsageCount` 相对偏差 < 15%；
- `carriedBursts` 相对偏差 < 10%。

**辅助判据**（丢包率，加绝对差兜底）：

- `burstLossRate` 相对偏差 < 10% **或** 绝对差 < 0.1 个百分点。

主判据全部满足则 go，按 τ/T_burst 归一化报告；不满足则 no-go：改为在物理速率下重跑（需开发 burst 级流量源），或降级结论为"仿真速率下成立"。

清单说的风险根源也对：`guardTime`、BCP 处理时延是绝对时间，不随线速率缩放，这正是要验证的东西。

## 三、代码复核五条：属实，但都不改代码

已逐条对照 `OBS_CoreControlLogic.cc` 第 136–376 行和 `OBS_CoreOutputHorizon.cc` 第 71 行。

### 3.2.1 与 3.2.2：`<` 与 `<=` 边界不一致 —— 属实，接受差异，只记录不改

确认：

- `findNearestLambda` 用严格 `arrivalTime > horizon`（`OBS_CoreOutputHorizon.cc:71`）；
- 颜色分支用 `horizon <= burstArrival`（`OBS_CoreControlLogic.cc:224`）和 `waitTime <= tau`（`cc:230`）。

没有实际影响的两点：

1. 恰好相等是连续随机流量下的零概率事件；确定性测试里的数值（waitTime 约 6.5 µs 对 τ = 20 / 2 µs）也远离边界。
2. **颜色分支在当前所有实验里是死代码**——本项目路由表波长全部是 `*`，只走通配分支。

改代码没有收益，反而要重新编译验证。在复核清单里写一句"已知差异，接受"即可。

**补充推论（交叉复核后补入）**：`AGENTS.md` 和多处文档引用的 FDL 判据表述为 `waitTime <= τ && FDL 空闲`，对应的是颜色分支 `cc:230`，但该分支是死代码。**实际生效的是通配分支的等价形式** `findNearestLambda(outPort, burstArrival+τ)`（`cc:198`），`phase2_code_guide.md` 已按通配分支的正确形式描述。`fdl_tests.ini` 的测试判据经过推演在通配分支下依然成立：τ=20 µs 时目标通道 horizon ≈ burstArrival+6.5 µs < burstArrival+20 µs，`findNearestLambda` 返回有效波长 → 回环；τ=2 µs 时 horizon ≈ burstArrival+6.5 µs > burstArrival+2 µs，返回 -1 → 丢弃。测试设计不受影响。

### 3.2.3：迟到判据与 `scheduleAt` 崩溃 —— 实验 C 前置任务（措辞已修正）

`burstArrival < simTime()` 为严格小于。严格 `<` 只改变了边界落在哪个分支——`arrivalDelta == 0` 时放行进入正常处理流程。**但这不意味着能"正常处理"**：紧接着第 255 行 `OXCConnectTime = burstArrival − guardTime/2`，当剩余 offset ∈ [0, guardTime/2)（即 0 到 0.5 ns）时，`scheduleAt()` 被要求调度到过去或当前时刻，OMNeT++ 4 运行时报错 `scheduleAt() called with time in the past`，仿真崩溃。

这是第一阶段就存在的老代码行为，不是 FDL 改动引入的。

**实验 A/B 不受影响**：offset 500 µs，十跳也耗不完。

**实验 C 的触发条件**（条件式，非一定会撞）：当 offset 扫描点恰为 `processingTime` 的整数倍（如 1 µs, 2 µs），经过足够多跳后剩余 offset 归零，即触发；或当扫描步长细到任何 offset < 0.5 ns 的点也会触发。

**第四阶段必崩**："边缘 offset=0" 意味着第一跳核心节点收到 BCP 时 `arrivalDelta` 就是 0，`OXCConnectTime` 一定落在过去。

判定：现在不动代码，但实验 C 前置任务清单必须包含：

1. 用 `offset=0` 跑一次 smoke 运行，实测复现崩溃（不只做纸面推导），留下精确的错误上下文。
2. 修复：把迟到判据从 `burstArrival < simTime()` 改为 `burstArrival < simTime() + guardTime/2`（或等价地在 `scheduleAt` 前加保护），覆盖 OXC 接通时刻。

### 3.2.4：FDL 入口只查一次 —— 确认无误，无需任何动作

OMNeT++ 单线程事件处理，查 horizon 和写 horizon 在同一次 `handleMessage` 里完成，下一个 BCP 事件必然看到更新后的值。不存在竞态。

### 3.2.5：丢弃统计口径 —— 需要做，补一句文档

属实：迟到丢弃（case 1）只进 `burstLossTotal`；竞争丢弃（case 2/3）同时进 `burstLossTotal` 和 `burstLossContention`。

`phase2_code_guide.md` 已经注明 total 含原因 1。建议再明确一句：实验 A/B 的主指标用 `burstLossContention` 除以 `burstsReceived` 更纯净，`burstLossRate`（基于 total）作为总体指标。

## 四、计划强化：两条采纳，一条本来就没要求改

### 第 6 周文献定位升级为 go/no-go —— 采纳

道理和 RateCheck 一样：预设"没有差异化 novelty 时怎么办"的出口，比事后慌乱强。输出必须包含"若无差异化 novelty 时的替代发表口径或收缩建议"，不停留在写一页陈述。

### 第 13 周输入 FDL 原型降级为可选 —— 采纳，且是全清单里最值钱的一条

第 12–14 周同时压着实验 C 和输入 FDL 两件事，是整个计划最脆弱的段落。把"时序模型（数学推导 + 小规模验证）"定为必交付、把"完整原型模块"定为后备，等于给计划买了保险。

### 论文并行线 —— 不改

清单本身也写了无需改动。
